# HomeChoice 用户流程

## 1. 流程目标

HomeChoice 的核心体验不是“搜索更多房源”，而是帮助用户对已经进入决策范围的 3–5 套房源形成可解释的判断。

完整流程需要同时表达三件事：

- 用户当前需要完成什么；
- 系统如何响应并降低下一步操作成本；
- 未来 AI 能力在哪些节点介入，以及用户如何保持最终控制权。

## 2. 端到端用户流程

| 阶段 | 用户行为 | 系统反馈 | 未来 AI 能力入口 |
| --- | --- | --- | --- |
| 进入产品 | 用户从首页了解产品价值并开始分析 | 说明产品适用于已有候选房源的用户，并展示 3–5 套房源的建议范围 | 根据入口场景解释产品能力，但不自动作出推荐 |
| 建立候选清单 | 用户新建一次比较，添加第一套房源 | 创建本次比较上下文，显示已添加数量、资料完整度和最多 5 套的限制 | 识别重复房源并提示合并，避免重复分析 |
| 手动录入房源 | 用户填写小区、位置、面积、户型、楼层和价格等字段 | 实时校验字段格式，区分挂牌价和预期成交价，提示缺失信息 | 根据已知字段提示可能需要补充的关键信息 |
| 上传房产截图 | 用户上传房源平台截图或中介资料 | 显示上传状态、文件预览和隐私提示 | 识别截图内容，提取小区、价格、面积、户型、楼层等结构化字段 |
| 确认提取结果 | 用户逐项检查 AI 提取内容，修改错误并确认 | 高亮低置信度字段，保留来源和修改状态，确认后更新房源资料完整度 | 给出字段置信度与提取来源；不得绕过用户确认 |
| 补充其他房源 | 用户继续添加房源，直到形成 3–5 套候选集合 | 使用统一卡片展示所有候选房源，提醒数量和资料差异 | 发现字段口径不一致时给出标准化建议 |
| 设置购房偏好 | 用户输入购房目的、预算、工作地点、通勤方式、教育需求和优先事项 | 将复杂权重转化为易理解的问题，并即时生成用户偏好摘要 | 将自然语言需求整理为结构化偏好；用户可修改确认 |
| 发起比较分析 | 用户确认候选房源和偏好后开始分析 | 显示分析进度，说明使用的数据范围和缺失项 | AI 负责解释与总结；确定性引擎负责评分、预算计算、排序和规则判断 |
| 查看结果概览 | 用户查看房源排名、推荐建议和主要差异 | 优先展示第一名、推荐理由、最大风险、BUY / WAIT / PASS 和可信度 | 将结构化结果转化为简洁说明，不得编造缺失事实 |
| 查看详细分析 | 用户打开单套房源的维度分析 | 展示各维度得分、通勤、价格、物业、教育、优势和注意事项 | 根据用户偏好解释分数变化，并标记需要线下核实的信息 |
| 提出假设问题 | 用户询问“如果预算变化”“如果换工作地点”等问题 | 展示条件变化前后的排名、分数和关键影响因素 | 理解自然语言假设，并调用确定性逻辑重新计算，不直接由模型猜测新分数 |
| 保存与回顾 | 用户保存本次分析，之后在历史记录中查看或继续分析 | 保存分析时间、候选房源、偏好快照、结果和版本信息 | 总结与上次分析的变化，提示偏好或房源信息是否已过期 |

## 3. 关键分支与异常流程

### 候选房源不足

- 当房源少于 2 套时，系统允许保存草稿，但不生成正式比较排名；
- 系统提示继续添加房源，不强迫用户立即完成。

### 候选房源超过上限

- 单次比较最多 5 套房源；
- 达到上限后禁用继续添加入口，并解释限制用于降低决策过载。

### AI 提取不确定

- 低置信度字段必须标记“待确认”；
- 用户可选择修改、保留为空或返回原截图检查；
- 未确认字段不得被包装成确定事实。

### 资料缺失

- 系统可以继续生成有限分析，但必须降低可信度；
- 结果页明确展示缺失信息及其可能影响；
- 缺失信息不应直接降低房源质量得分。

### 用户偏好发生变化

- 用户可返回偏好页修改条件；
- 系统生成新的分析版本，不覆盖原历史记录；
- 结果需要展示排序变化及变化原因。

## 4. 体验原则

- 每一步只要求用户处理当前决策所需的信息；
- AI 自动化必须可见、可检查、可修改；
- 预期成交价在决策中的层级高于挂牌价；
- 通勤以“家到实际工作地点”为基础，而不仅是地铁距离；
- 物业服务与小区硬件质量作为独立维度；
- 教育信息必须区分“已核实”和“待确认”，不承诺入学资格；
- 结论必须同时说明推荐理由、风险和适用条件。
